## 整合規格時的裁決
- **R-01 分區串流**：Phase 1 不實作。`Placement` 一律帶 `regionId`，`chunkId` 選填預留。Phase 1 量測超出預算才做。
- **R-02 存檔位置**：正式版由 Electron 主程序寫 `userData` 下的 JSON（原子寫入加 `.bak` 備份）。IndexedDB 只用在網頁開發模式。（Phase 2 實作）
- **R-03 迷霧**：權威狀態存三段（濃／淡／清 = 1.0／0.5／0.0），渲染層的 `uMist` 做時間與空間插值。

## 技術決策（任務 1A）
- **T-01 TypeScript 固定 6.0.x**：typescript-eslint 8.71 只支援 TS 6.1 以下，所以不升級 TS 7。等 typescript-eslint 支援後再升。
- **T-02 不使用 vite-plugin-electron**：主程序與 preload 用 esbuild 編譯（`scripts/build-electron.mjs`、`dev-electron.mjs`）。esbuild 本來就是 Vite 的依賴，不需要額外套件。preload 在 sandbox 下必須是 CommonJS，所以輸出成 `.cjs`。
- **T-03 效能面板自製**：沒有用 r3f-perf（規格允許「r3f-perf 或 stats 面板」），因為 r3f-perf 對 R3F 9 和 React 19 的支援不確定。自製面板直接讀取 `gl.info`，以 250 ms 間隔寫入 DOM。
- **T-04 Tone mapping 用 Neutral**：R3F 預設的 ACES 會讓綠色變灰，不符合規格要求的高飽和卡通風格。
- **T-05 所有套件放在 devDependencies**：Renderer 已由 Vite 打包，主程序沒有執行期依賴，這樣打包時不會把 node_modules 放進 asar（從 128 MB 降到 1.3 MB）。之後主程序如果需要執行期套件，再放進 `dependencies`。
- **T-06 新增 zod 依賴**：在技術棧清單內，用於資料與存檔驗證。
## 技術決策（任務 1B）
- **T-08 玩家角色 = KayKit Adventurers「Rogue_Hooded」**：CC0、GLB 內含 76 個與骨架同源的動畫，涵蓋規格 4.6 全部需求，免去 Mixamo 套 Q 版的變形風險；兜帽造型符合「迷路的旅人」。原始比例約 2 頭身（頭身比與規格「約 3 頭身」相近，使用者已同意），縮放 0.72 → 身高約 1.6 m。同系列另有 Knight / Mage / Barbarian / Rogue，可作為 NPC。
- **T-09 Physics `timeStep="vary"`**：角色控制器在 useFrame 計算位移，每幀對應一次物理步進；固定步長在 120 Hz 螢幕上會讓兩次 `setNextKinematicTranslation` 只生效一次。
- **T-10 角色外觀與剛體分離**：外觀依本幀計算的位置擺放（不等物理步進後的剛體同步），攝影機也讀同一份位置，避免一幀落差造成抖動。
- **T-11 移動規則放在 game-core**：`stepLocomotion` 為純函式（狀態 + 輸入 → 新狀態 + 位移），Rapier 只做碰撞修正；日後伺服器可重用同一份規則驗證移動。
- **T-12 測試的 TypeScript 設定分離**：`tsconfig.json`（App，不含 Node 型別）與 `tsconfig.test.json`（測試，含 Node 型別），避免 App 程式誤用 Node API。
- **T-13 端對端以 Node 腳本 + Playwright `_electron` 撰寫**（`e2e/*.e2e.mjs`），不引入 `@playwright/test` 執行器；需要時再評估。

- **T-07 佔位 GLB 由程式產生**：還沒有確定授權素材前，先用無外部依賴的腳本產生松樹 GLB，用來驗證 GLB 載入與 instancing 流程。（1C 已換成正式素材並移除）

## 技術決策（任務 1C）
- **T-14 環境素材 = KayKit Medieval Hexagon + Dungeon Remastered**：與角色同作者、同風格、CC0，可直接從 GitHub 取得。KayKit Forest Nature Pack 只在 itch.io 提供，無法以腳本下載，因此先用 Hexagon 包內的樹與岩石；Phase 1 風格判定後再決定是否替換。
- **T-15 碰撞形狀寫在 prefab，碰撞體以命令式 API 管理**：大量靜態物件不建立 React 元件，`EnvironmentColliders` 依玩家距離直接呼叫 `world.createCollider / removeCollider`（30 m 啟用、35 m 移除、每 0.25 秒更新），避免每次增減都觸發 React 重新渲染。
- **T-16 互動用空間格網查詢，不用 Rapier sensor**：互動對象數量多且全為靜態，格網查詢（`SpatialGrid`）是純 TS，可在 game-core 測試、日後伺服器重用；規格 6.2 允許「sensor 或空間查詢」。
- **T-17 互動規則先以最小指令 / 事件實作**：`handleInteract`（純函式）→ `WorldEvent[]` → `applyWorldEvents`，由 `worldStore` 呼叫。Phase 2 再包成完整的 `Authority` 介面，規則不需改動。
- **T-18 安全點採「沿途記錄」**：不在資料中手動標記安全點；記錄玩家實際站穩過的位置，保證重置點可站立、不在碰撞體內。
- **T-19 `uMist` 以材質 `onBeforeCompile` 實作去飽和**：尚未引入後處理（Phase 1 收尾才做），先在每個 toon 材質的霧計算前插入去飽和與冷色偏移；所有材質共用同一個 uniform 物件。後處理加入後，可把畫面整體色調移到 color grading，材質層保留植被去飽和。
- **T-20 迷霧可見距離以幾何插值**：線性插值時前半段幾乎看不出變化；幾何插值讓滑桿每一段的體感變化較平均。濃霧的可見距離 75 m（46 m 時觀景點整片灰，無法做美術比對）。

## 修正與 Phase 1 收尾（2026-10-13）
- **T-21 Rapier 物件在 effect 內建立、cleanup 釋放**：開發模式的 React StrictMode 會「掛載 → 卸載 → 再掛載」。角色控制器原本用 `useMemo` 建立、cleanup 釋放，再掛載時拿到已釋放的控制器，每幀拋錯，畫面停住（使用者回報「轉視角後畫面不動」）。正式版沒有 StrictMode，原本的端對端測試都跑正式版所以沒抓到。改為在 effect 內建立；新增 `e2e/dev.e2e.mjs` 以開發模式實際操作，任何未捕捉錯誤都會失敗。之後所有 WASM / GPU 資源都依此模式。
- **T-22 未捕捉錯誤顯示在畫面上**：`window` 的 `error` / `unhandledrejection` 寫入 `errorStore`，由 `ErrorOverlay` 顯示，避免遊戲無聲凍結。
- **T-23 村莊用 KayKit Medieval Hexagon 的建築與雜物**：與樹木同一包、共用同一張貼圖，風格一致。碰撞形狀新增 `offset`（模型幾何不在原點時使用，例如柵欄位於六角地塊邊緣）。村莊周圍地形壓平（`VILLAGE_CENTER`、`VILLAGE_RADIUS`）。
- **T-24 地形 splat 在 shader 內以程式產生，不用貼圖**：規格 4.2 寫「splat map + 手繪貼圖」。目前沒有參考圖與手繪貼圖素材，所以先以世界座標雜訊產生「筆刷感」色塊、泥土路（邊緣擾動、碎石）與陡坡岩石，權重來自頂點屬性（到小路的距離）與法線。好處是任何距離都沒有貼圖拉伸、不需載入資產；使用者確定畫風後，可把同一套權重改成取樣手繪貼圖。
- **T-25 草花：16 m 區塊的 InstancedMesh + shader 風動與距離縮入**：草叢顏色在 vertex shader 取自與地形相同的函式，根部與地面無縫；法線一律朝上（雙面材質背面不會變黑）；超過可見距離時整株縮入地面，不用半透明排序。散佈為 game-core 純函式（抖動格點、固定種子、避開小路與碰撞體），有單元測試。
- **T-26 遠山用程式產生的環狀山脈，不用 KayKit 山模型**：Hexagon 包的山是六角柱狀岩壁，放大當背景時像灰色牆面（已截圖確認後放棄）。改為兩層環狀帶狀網格（近層綠色丘陵、遠層藍紫山峰），以「空氣透視」混向地平線色而非場景霧，混合比例跟隨 `uMist`。地圖外加一圈低於邊緣丘陵的地面延伸，從觀景點往外看不會有空洞。雲用 KayKit 雲模型，緩慢飄移。
- **T-27 陰影相機跟隨攝影機前方焦點**：原本單一陰影貼圖覆蓋 140×140 m，近景鋸齒與樹冠陰影條紋（shadow acne）明顯。改為只涵蓋攝影機前方 ±38 m，焦點對齊陰影貼圖像素格避免移動時閃爍；normalBias 0.09。
- **T-28 新增 `@react-three/postprocessing` 3.2.0、`postprocessing` 6.39.5**：規格技術棧已列；版本確認支援 R3F 9 與 three 0.186。Bloom（低強度、高門檻）、飽和度（晴朗 +0.1 → 迷霧 −0.2，跟隨 `uMist`）、暗角、Neutral tone mapping；composer 開 4× MSAA。低畫質不啟用。
- **T-29 畫質三級的數值放在 game-core**（`settings/quality.ts`）：草花密度與距離、後處理、陰影解析度、像素比上限。Phase 1 設定不存檔（Phase 2 與存檔系統一起做）；`?quality=low|medium|high` 可指定初始畫質。
- **T-30 Phase 1 先做最小主選單與暫停選單**：Phase 1 驗收要求「可連續遊玩並回主選單」。主選單（開始遊戲、畫質、離開遊戲）以緩慢環繞的實際場景為背景；遊玩中按 Esc 或滑鼠鎖定被解除時開啟暫停選單（繼續、畫質、回主選單）。流程狀態轉換為 game-core 純函式。還沒有存檔，所以回主選單再開始會重置世界與角色（選單上有提示）。`?play=1` 略過主選單（測試與截圖用）。
- **T-31 關閉視窗即結束程式（含 macOS）**：遊戲只有一個視窗，沿用 macOS 文件型 App「關窗不結束」的慣例沒有意義，也會讓主選單的「離開遊戲」看起來沒反應。
- **T-32 滑鼠鎖定的端對端檢查依環境略過**：Chromium 只在視窗位於作業系統前景時允許滑鼠鎖定；開發機有人使用其他視窗時，連最小測試頁都會被拒絕（`WrongDocumentError`，已驗證）。此時 `dev.e2e` 會把「鎖定滑鼠」標為略過並說明原因，改用除錯 API 以相同換算轉動攝影機，其餘流程照常驗證。

## Phase 2（2026-10-13 起）
- **P-01 進入 Phase 2**：使用者指示「依進度接續下一階段開發、一直做到結束」，視為同意 Phase 1 驗收、進入 Phase 2。仍待使用者處理的項目（風格參考圖比對、B 級機器量測）保留在 `PROGRESS.md`「下一步」，不阻擋後續階段；Phase 5 美術完善時一併做風格判定。
- **T-33 Authority 與規則**：`game-core/authority/rules.ts` 的 `handleCommand(state, command, ctx) → events` 與 `applyEvents(state, events) → state` 皆為純函式；`ctx` 注入世界查詢、物品、掉落表與亂數（測試用固定種子，日後伺服器用自己的）。`LocalAuthority`（`authority.ts`）保存狀態、送指令、通知訂閱者，放在 game-core 以便伺服器重用。UI / 3D 只讀 `useGameStateStore`（權威狀態的唯讀鏡像），取代任務 1C 的 `worldStore`。Phase 6 的 `RemoteAuthority` 實作同一介面（`send / subscribe / getState`）。
- **T-34 背包「全部放得下才成功」**：`addItems` 放不下任何一部分就回傳 null、狀態不變。採集與開箱在背包滿時被拒絕，物件維持原狀（樹不會被砍掉、寶箱保持關閉），唯一獎勵不會遺失。
- **T-35 採集指令在動作揮下時送出**：按 E 先轉身並播放動作（砍樹 / 敲石頭用 attack，摘花採藥用 interact），0.45–0.5 秒後才送出指令，物件在揮下的瞬間變成樹樁或消失；結果仍完全由權威層決定。被拒絕時以通知顯示原因（例如背包已滿）。
- **T-36 遊戲時間由權威層保存**：`GameState.time` 只在遊玩中前進（`GameClock` 每秒送 `AdvanceTime`，主選單與暫停時停止），重生時間 `respawnAt` 以遊戲時間計，存檔後讀回仍正確。玩家站在重生位置 2.5 m 內時延後重生，避免卡進碰撞體。
- **T-37 樹樁與採集後碰撞**：KayKit Hexagon 包內的 `tree_single_A_cut / B_cut` 當樹樁（同包同貼圖）。prefab 的 `harvest.harvestedModel / harvestedCollision` 宣告採集後的外觀與碰撞；`EnvironmentColliders` 依狀態切換。樹樁矮於自動上台階高度時角色可以踩上去（不會穿進去）。
- **T-38 花叢與草藥為程式產生的模型**：素材包沒有可採集的花與草藥，以葉片面片 + 星形花冠組合（`render/proceduralModels.ts`，prefab model 為 `procedural:<id>`），比草地上的裝飾小花大很多，一眼可辨。與植被相同使用朝上的法線、不接收陰影（薄面片自我遮蔽會發灰）。不放進 GLB 是為了不需要額外的建模工具鏈；若之後找到風格一致的 CC0 模型可直接換掉 prefab 的 model。
- **T-39 物品圖示用 SVG 元件**：`ui/ItemIcon.tsx` 依 `items.json` 的 `icon` 欄位繪製，任何解析度都清晰，不需要圖片資產與授權登錄。
- **T-40 存檔分層**：game-core 負責格式（`save/schema.ts`，zod）、轉換（`convert.ts`：只存與預設不同的物件差異）、版本遷移（`migrate.ts`）與「主檔 → 備份 → 損壞」的讀檔決策（`load.ts`）；儲存實作只搬資料：Electron 主程序 `electron/saveFiles.ts`（`userData/saves/<slot>.json`，寫暫存檔並 fsync → 主檔改名為 `.bak.json` → 暫存檔改名為主檔，任何一步中斷都至少留下完整的主檔或備份），網頁開發模式 IndexedDB（主檔與備份同一 transaction）。欄位名稱在主程序以白名單正則再驗證一次，避免路徑穿越。
- **T-41 讀檔時容忍資料檔變動**：存檔內已不存在的物件或物品只略過並在主控台警告，不讓整份存檔失效；格式不符（zod）才視為損壞。
- **T-42 自動存檔時機**：採集 / 開箱後 2 秒（連續採集合併成一次）、遊玩中每 60 秒、回到主選單前；另有暫停選單的「儲存遊戲」與「匯出存檔」。寫入依序排隊、非同步，不阻塞渲染。規格提到的「區域切換、任務完成」於 Phase 3 有區域與任務後加入。
- **T-43 第 1 版存檔沒有真正的遷移**：Phase 2 是第一個存檔格式，遷移框架以模擬的三版遷移鏈測試（依序套用、缺版本號、比遊戲新、缺少遷移函式）；Phase 3 加入任務與各區域迷霧時會是第一個實際的 v1 → v2 遷移。
- **T-44 端對端測試使用獨立的存檔與使用者資料夾**：`MISTWOOD_SAVE_DIR`、`MISTWOOD_USER_DATA_DIR`（主程序讀取），每次啟動用暫存資料夾，測試不會讀到或覆蓋玩家的存檔與 IndexedDB。`?storage=indexeddb` 讓端對端測試在 Electron 中驗證網頁開發模式的儲存實作。
- **T-32 補充**：當測試視窗真的取得滑鼠鎖定時，Chromium 會在自動化的模擬滑鼠移動約 2 秒後解除鎖定（以 Phase 1 版本驗證過，同樣發生，人工遊玩不受影響）。`dev.e2e` 改為只在鎖定期間做一次短暫的滑鼠轉動檢查，之後解除鎖定、以除錯 API 繼續；檢查途中鎖定被系統解除時記為略過。
- **T-45 教學進度是權威狀態**：`GameState.tutorial`（move → interact → harvest → inventory → done），以 `AdvanceTutorial { from }` 指令前進（from 必須等於目前步驟，重複送出不會跳步）。完成條件是 game-core 純函式；移動距離與「開過背包」是本機訊號，由 `TutorialSystem` 每 0.2 秒檢查後送指令。開箱與採集看權威狀態，先做了也算完成。
- **T-46 第一個實際的存檔遷移 v1 → v2**：加入 `tutorial` 欄位；v1 存檔建立時還沒有教學，玩家已在遊玩中，遷移時視為已完成（`done`）。測試以實際的 v1 格式存檔驗證讀入後其他內容不變。
- **T-47 按鍵重新配置**：game-core `rebind()` 純函式：每個動作主要 / 次要兩格，同一按鍵被其他動作使用時從該動作移除並回報；Esc 保留給暫停與關閉視窗，「暫停」不開放修改；不能清掉最後一個按鍵。按鍵設定存於設定存檔的選填欄位 `bindings`（省略表示預設），讀回後套用到輸入層。所有提示文字（操作說明、互動提示、教學、背包關閉提示）以 `{interact}` 等變數顯示目前的按鍵。
- **T-48 設定畫面取代選單內的畫質切換**：主選單與暫停選單改為「設定」按鈕，畫質與按鍵集中在設定畫面；設定畫面以 capture 階段攔截按鍵，開啟時按鍵不會傳到暫停選單與遊戲輸入。音量在 Phase 5 加入音效時一起放入。

## 技術決策（Phase 6）
- **T-93 地圖邊界做法**：可玩區為圓角方形（半寬 74 m、圓角 10 m），定義在 game-core `world/bounds.ts`，碰撞、迷霧牆、提示與測試共用。碰撞是沿邊界每約 6 m 一段的靜態方塊（內側面剛好在邊界上、高 40 m），一次建立、不依距離啟用（約 50 個，數量固定）；登記在 `cameraIgnoredColliders`，攝影機可以穿出牆外，不會在邊界被拉近。迷霧牆是單一網格的自訂 shader（透明、不寫深度、不受場景霧影響，顏色每幀取場景霧色），1 個 draw call。牆外裝飾樹使用新 prefab `tree_edge_round / tree_edge_tall`（同模型、`collider: none`、不可採集），以獨立種子附加在 `gen-placements.ts` 最後。`KILL_Y` 掉落重生仍保留。
- **T-94 日夜的時鐘不另存**：時刻完全由已存檔的 `GameState.time`（遊玩秒數）推導，`time = 0` 為 08:00，白天與夜晚以分段線性換算（G-04）。舊存檔不需遷移，讀檔後時段自然一致。權威狀態每秒才前進一次，`GameClock` 在兩次之間把本機累積的秒數加上去，太陽平滑移動（`timeRuntime`）。睡覺與除錯設定時鐘都是「把時間往前推進到下一個該時刻」，與一般的時間前進同一條規則（重生、回血、生成照常結算），時間不會倒轉。日月軌道在地平線上下各為半個正弦（白天 13 小時、夜晚 11 小時長度不同，單一正弦會讓月亮在白天冒出來）。
- **T-95 時段外觀疊在迷霧之下**：`timeLook` 依時鐘在 10 個關鍵時刻之間平滑插值，結果作為 `mistLook` 的晴朗端；迷霧端的顏色乘上時段色調、強度依時段等比例縮放，所以「夜晚的濃霧」是暗藍灰而不是發亮的白霧。`mistLook` 的呼叫端（Lighting、Sky、Backdrop）不需修改呼叫方式，由 Lighting 每幀先 `updateTimeLook`。白天（08–16 時）的值與原本的晴朗色票完全相同，既有畫面與測試不受影響。夜晚不做真黑夜（月光 0.75 + 半球光 1.05，偏藍），符合 Bible 13.5「不可讓玩家看不見道路與攻擊提示」。室內固定使用正午的外觀。
- **T-96 夜晚發光不用即時點光源**：星光燈、營火的夜晚光暈與螢火蟲都是加法混合的 HDR 點精靈（各一個 draw call），交給 Bloom 產生光暈；即時點光源預算（最多 2 盞）留給魔法特效（GAME_DESIGN 6.2）。畫質預設新增 `particleBudget`（低 800／中 2000／高 3000），螢火蟲取 6%。村屋窗燈需要模型窗戶分區，延到 Phase 7。
- **T-97 近戰招式是資料、命中仍由規則判定**：`data/weapons.json` 定義三種武器各一組輕擊連段（3 招）與一個重擊（含冷卻）；每招指定角色 GLB 內既有的動畫片段（KayKit 的 Unarmed / 1H / Dualwield / 2H 系列，不需要新素材）、播放速度、動作鎖定時間、命中時間、範圍與扇形角度、擊退、命中停頓、往前衝。連段與重擊冷卻是 game-core 純函式（`startLight` / `startHeavy`），本機計算；命中仍以招式範圍判定（不依賴動畫事件），權威層只接受「屬於目前裝備武器」的招式 id 並以資料結算傷害。舊的 `attack` 招式 id 不再接受；預設裝備單手劍，存檔 v8 加入 `loadout.weapon`（v7 遷移為單手劍）。
- **T-98 武器模型直接重用角色包的節點**：短刀是玩家模型本身原本隱藏的雙刀；單手劍從同系列 Knight.glb 複製 `1H_Sword` 節點，掛到玩家骨架的右手 handslot（兩個模型的 handslot 局部座標相同，所以位置與握法正確）。注意 GLTFLoader 會移除節點名稱中的「.」，`handslot.r` 載入後名稱是 `handslotr`。揮砍拖尾以刀身包圍盒最長軸的遠端為刀尖，每幀記錄刀尖與刀身的世界座標，畫成加法混合的帶狀網格。
- **T-99 打擊感**：命中時角色動畫停頓 40–100 ms（只停玩家的 mixer，世界照常）、鏡頭震動（設定可關閉，`settings.cameraShake`，設定檔欄位選填、不升版本）、刀劍火花 / 拳腳衝擊塵（固定 6 個的物件池）。出招時輕度鎖定前方 100° 內最近的敵人；動作結束前 0.3 秒內的攻擊輸入會排隊（先行輸入），連段不會因為按早一點而斷掉。手把：X 輕擊、RT 重擊、十字左依序切換武器（原本 RT 也是輕擊）。
- **T-100 魔法以星光值施放、命中由規則判定**：`data/spells.json` 定義法術（種類 nova / bolt、星光消耗、冷卻、蓄力與動作時間、傷害、範圍、擊退、彈體參數、施法動畫、特效主色）。施放流程：本機檢查冷卻 → `CastSpell` 指令由權威層檢查並扣除星光值（存檔 v9 `combat.mp`，每秒回 6）→ 腳下魔法陣蓄力 → 發動。範圍法術在發動瞬間以範圍判定；追蹤彈在本機模擬飛行（轉向速率、射程），碰到敵人時送 `AttackEnemy`（法術 id），傷害由資料結算。舊的 `skill` 攻擊與 `PLAYER_STATS.attack / skill` 移除。被魔法擊敗的迷霧生物額外播放「淨化」（金色光點上升，呼應 Bible「恢復比破壞重要」）。權威層介面不回傳結果（保留給之後的遠端權威），施放是否成功以星光值是否被扣除判斷。
- **T-101 VFX 引擎自製、不新增依賴**：遊戲邏輯只把特效請求放進 `vfxQueue`（不碰 three.js），`VfxSystem` 每幀取出並以固定資源播放：GPU 粒子池（instanced 四邊形，起點 / 速度 / 顏色 / 壽命 / 大小 / 重力 / 阻力 / 形狀在發射時寫入一次，運動與淡出在 vertex shader 以時間計算；環狀緩衝，容量 = 畫質的 `particleBudget`；加法混合 + HDR 顏色交給 Bloom）、程式產生的魔法陣 shader（雙環、反向旋轉的符文刻度、六芒星）與衝擊波 shader（噪聲擾動的擴散光環）物件池、點光源 2 盞（中高畫質，常駐、閒置時強度 0，避免切換燈光數量造成全部材質重新編譯）。所有池內物件在載入後前 3 幀以全透明畫一次，shader 提前編譯。施法時右手換成 Mage.glb 的魔杖。
- **T-102 流星雨與手把的法術按鍵**：流星雨（C）的落點由 game-core `meteorPlan` 決定（前 6 顆隨機散落在範圍 75% 內、間隔 0.16 秒，最後一顆在正中心、晚一個間隔、範圍 4.5 m），本機依時間推進每顆流星（從撞擊點右上方 26 m 處加速斜落）；每次撞擊都以範圍判定命中、送出攻擊指令（每顆 30 傷害）。蓄力 0.8 秒期間前方地面先出現落點魔法陣，直到流星落完才消失（Bible 11.2：攻擊必須有預兆）。落點中心拉回地圖邊界內。手把改為每個法術一個固定按鈕（RB 星光衝擊、十字下 星屑飛彈、R3 流星雨），不做「選擇法術再施放」：手把配置本來就是固定的（T-87），少一層操作也比較直覺。

- **T-164 潮之共鳴與戰後的璃漪**（任務 9E-2，Bible §7.4 `quest_lake_003`、§7.5、§7.7 `prop_lake_temple_core`）：比照 8D-2 森林根源石：神殿中央的潮之共鳴裝置（從神殿模型拆成獨立的 `activate` 物件，`afterBoss` 璃漪）擊敗璃漪後才喚得醒，取得 `item_tide_resonance` 潮之共鳴，成為任務的第二個目標。共鳴的特效與提示原本寫死成苔咚的根源石，改成依頭目的 `textKey` 取用（璃漪：湖藍色、「共鳴球亮了起來」）。戰後的璃漪是 NPC（擊敗後出現，縮小、安靜地在石台上方游動），說 Bible 的戰後台詞「回聲不是命令……」；任務完成後改說湖面映出的是現在。Bible 的獎勵「湖泊家園裝飾配方」做成兩個建造物：蘆葦盆栽（花 × 2、水之精華 × 1）與鏡殼燈（鏡殼片 × 2、湖珠 × 1）；建造物的 `unlock` 新增 `completed`，要完成任務才出現在建造選單（7K 的花圃是接了任務就出現）。「風語草原通行」等 Phase 10 再做。另外修正鯉龍的頭沒有頂點色（在戰鬥中顯示成黑色）。
- **T-165 風語草原的地圖與場景**（任務 9F，Bible §8.2–8.3、§8.7）：第四張地圖放在世界座標 (6000, 0)（同 T-117，與澄鏡湖相距 2000 m），地圖大小沿用其他地圖的 320 m（可玩區 ±148 m），不用 Bible 建議的 450 × 350：探索紀錄、地形取樣、小地圖與世界地圖都以同一個大小為前提，草原的開闊感改用起伏平緩、樹少花多、遠景不擋視線來表現。地形 `meadowTerrain.ts`：西側入口（古風帆）、中央偏南的風車聚落平地（三座停擺的 KayKit 風車——prefab 不加 `animate`，之後的任務讓它轉——農舍、穀倉、水井、兩片農田）、北邊頂面 13 m 的浮石山脊（邊緣陡峭走不上去，之後靠上升氣流）、東側抬高 5 m 的風向塔台地（西側一條最大坡度 0.19 的緩坡）與北端的競技場（石墩外圈南側留缺口當入口）、彎月石拱。通行：澄鏡湖東岸的古風帆，完成 `quest_lake_003`（喚醒潮之共鳴）才能通過；世界地圖的古風帆地標也在那之後出現。新區域 windy_hills（預設）、windmill_hamlet、floatstone_ridge（沿山脊的帶狀範圍）、wind_tower、golem_arena，草原與聚落淡霧、其他濃霧；存檔 v16。散佈物與邊界樹的 placement id 用 `wm_` 前綴（晨曦谷地的草原已經用了 `meadow_tree` 等）。模型都是程式產生（`render/meadowModels.ts`），植被與岩石沿用 Kenney Nature Kit。風訊號旗模型已做好，之後的任務（`quest_meadow_001`）才放置。

## Phase 11 多人連線（2026-10-15 起，使用者提供〈3D RPG 多人連線技術規劃與 Claude Code 實作規格〉）
- **T-166 Colyseus 取代 Socket.IO，多人提前開始**：GAME_DESIGN §9 原本把多人列為最後的 Phase 11（Socket.IO + `RemoteAuthority`）。使用者要求現在開始，並指定依新的規劃文件：Colyseus 0.18 + TypeScript，獨立的遊戲伺服器程序（`server/`），Web 與 Electron 共用同一份客戶端模組（`src/net/`），共用協定放在 `src/game-core/net/`（前端不會匯入伺服器程式）。用 `@colyseus/core`、`@colyseus/ws-transport`、`@colyseus/schema`、`@colyseus/sdk`（舊的 `colyseus.js` 已改名），不用 `colyseus` 總包（會帶進 Redis、monitor、playground）。schema 用 `schema()` 定義，不用 decorator（esbuild / Node 不需特別設定）。`@colyseus/schema` 固定 5.0.36，不用前一天才發布的 5.0.40（不加 pnpm 的 minimumReleaseAge 排除）；`msgpackr-extract`（選用的原生加速）不允許安裝腳本。9F 風語草原保留原本的 T-165。
- **T-167 沿用 pnpm，不換成文件建議的 bun**：repo 已有 `pnpm-lock.yaml`、`pnpm-workspace.yaml`（Electron / esbuild 安裝腳本的允許清單與 release age 設定），所有腳本、e2e 與續作文件都依 pnpm；文件也要求遇到這種情況先回報、不換 lockfile。
- **T-168 移動由客戶端模擬、伺服器驗證**：伺服器沒有地形與碰撞（Rapier、樹、建築），若照文件字面「客戶端只送輸入、伺服器模擬」，伺服器算出的位置會和客戶端的碰撞結果一直衝突。改為客戶端照舊用 Rapier 移動並回報位置，伺服器用自己的時鐘驗證：水平 `(跑步 6.2 + 最快突進 5.5) × 1.25 m/s`、垂直 `max(起跳, 重力) × 1.25 m/s`、經過時間上限 1 秒、外加 1 m；位置必須在某張地圖的可玩區（外推 4 m）或某個室內 30 m 內；地圖與室內由伺服器判斷，不採用客戶端的說法。不通過就保留上一個合法位置並送 `correction`（每 250 ms 最多一次），客戶端拉回去。合法的位置跳動（地圖出入口、進出室內、落水重生、讀檔、新遊戲、伺服器修正）由 `Player.tsx` 把 `playerRuntime.warpSeq` 加一，客戶端改送 `warp`，伺服器只檢查間隔 ≥ 1.5 秒與落點範圍（之後再依出入口與重生點資料收緊）。客戶端無法用任意座標瞬移、也不能設定血量等欄位（`strictObject` 拒絕多餘欄位）。
- **T-169 在場層與遊戲進度分開、單一世界房間**：多人只同步誰在、在哪、什麼動作；任務、背包、戰鬥、存檔仍是各自的 `LocalAuthority` 與本機存檔（GAME_DESIGN §1：單人完整、多人加成）。單一房間 `world`（選項 `instanceId`、上限 16 人），每個玩家帶伺服器判斷的 `map` / `location`，客戶端只顯示同地圖、同室內的人，為之後依地圖分房或 AOI 預留。加入時帶目前位置，在可玩範圍內就採用（讀檔後可能在其他地圖），否則指派晨曦谷地出生點。遠端玩家沒有碰撞體。
- **T-170 遠端玩家的插值**：每則移動帶著算出該位置那一幀的時間（`playerRuntime.positionAt`），接收端在送出端的時間軸上插值、呈現延遲 100 ms；時鐘差取延遲最短的那一包、每次允許往上調 0.25 ms，變化時以最多 10% 的速度追上。量測過程（e2e 每一幀取樣）：用收到的時間當快照時間，送出與伺服器更新都是 50 ms，相位差讓速度在 0 與 2 倍之間跳（最高 12.2 m/s）；改用送出時間後剩下開頭的跳動——停著時 1 秒才送一次，開始走時從 1 秒前的位置一路內插（16.7 m/s）——補一個「還在原地」的快照解決；用送出計時器的時間而不是那一幀的時間，掉幀時會差一幀。延遲改 150 ms 沒有改善，維持 100 ms。結果：穩定時 2.8–3.3 m/s（走路 3 m/s），機器很忙時偶爾停約 0.1 秒再追上（列為已知問題）。
- **T-171 連線 UI 與設定**：伺服器位址優先序 `?server=` > 建置時 `VITE_GAME_SERVER_URL` > `ws://localhost:2567`；`vite.config.ts` 把 `VITE_GAME_SERVER_URL` 的 ws/http 來源加進 CSP 的 `connect-src`（Colyseus 先發 HTTP matchmake 再開 WebSocket），localhost 任何埠一律允許。暫停選單新增「多人連線」面板（顯示名稱、伺服器、連線 / 中斷 / 重新連線、房間內的人；名稱記在 localStorage）；小地圖下方的連線狀態（狀態、人數、斷線原因、「重新連線」）；他人加入 / 離開的通知；`?mp=1&mpName=` 在場景就緒後自動連線（測試與多分頁試玩）；回到主選單時中斷。第一階段斷線後不自動重連（SDK 的 reconnection 關閉，伺服器不保留座位），由玩家按「重新連線」重新加入。名牌用 drei `Html`（不需要字型檔）。
- **T-172 斷線續玩與自動重新加入**（任務 11C，〈多人連線規劃〉Phase 3）：非自願斷線時伺服器 `onDrop` 保留座位 20 秒（`allowReconnection`），角色留在原地、狀態新增 `online: false`，其他人看到名牌變淡並標示「（連線不穩）」，不顯示離開；逾時才 `onLeave` 移除。客戶端開啟 SDK 的自動重連（最多 8 次、間隔上限 3 秒，總長約 15 秒，短於伺服器保留的 20 秒），重連回來是同一個 sessionId；斷線期間自己走動過，重連後第一則改送 `warp`，伺服器在 `onReconnect` 清掉 warp 間隔限制允許這一次。座位沒了（伺服器重啟、Render 休眠喚醒、保留逾時、自動重連失敗、伺服器關機的 4001）時自動重新加入：間隔 1、2、4、8、10 秒（之後每 10 秒），最多 3 分鐘（涵蓋 Render 免費方案喚醒時間），之後才顯示「重新連線」按鈕。連線狀態新增 `reconnecting`（「重新連線中…」）；重連中不送位置（SDK 會把訊息排隊、重連後一次送出一堆舊位置）。SDK 每次重試失敗都會再觸發 `onDrop`，只在剛斷線時提示一次。SDK 的 `minUptime` 預設 5 秒（加入不滿 5 秒就斷線時不重連、直接放棄），改成 1 秒：原本剛連上就斷線會拿到新的 session，舊座位還在保留期間時其他人會看到兩個同一個人（完整 e2e 的紀錄抓到：A 加入約 5 秒時剪斷網路，SDK 印出「Room has not been up for long enough」）。關閉視窗 / 分頁時（`pagehide`）主動離開，其他人馬上看到離開，不必等 20 秒。已知限制：自動重新加入是新的 session，若舊座位還在保留期間（例如重連失敗但伺服器沒重啟），其他人最多 20 秒會同時看到舊的（離線）與新的同一個人。
- **T-173 依網路抖動調整的呈現延遲**（任務 11C）：每個遠端玩家各自記錄快照「比最快的那一包晚到多少」（收到時的時鐘差 − ClockSync 的目標值），目標延遲 = 送出間隔 50 ms + 最近 40 包的第 95 百分位 + 20 ms，限制在 100–300 ms；往上調每 1 ms 最多加長 0.5 ms（播放放慢一半，避免快照還沒到就停住），往下調每 1 ms 最多縮短 0.05 ms（播放快 5%，抖動通常一陣一陣，不要一好轉就縮短）。網路穩定時維持原本的 100 ms（T-170 的行為不變）。e2e 以代理加入 0–150 ms 的隨機延遲時，延遲升到約 150–180 ms，移動仍連續。
- **T-174 依出入口資料驗證瞬移落點延後到 Phase 6**：原本列在 Phase 3。讀檔的落點是存檔裡的任意位置，無法只用出入口、室內與重生點的資料驗證；要等存檔改由伺服器保管（Phase 5 雲端存檔）或伺服器權威（Phase 6）時一起做。目前仍只檢查間隔 1.5 秒與落點在可玩範圍內（T-168）。
- **T-175 部署設定與連線來源允許清單**（任務 11D，〈多人連線規劃〉Phase 4）：前端放 Vercel（`vercel.json`：先 `npm install -g pnpm@12.11.2` 再安裝——`pnpm-workspace.yaml` 的 `allowBuilds` 需要 pnpm 11 以上，不依賴平台依 lockfile 自動選的版本；`pnpm build:web`、輸出 `dist`、`/assets/*` 長效快取），遊戲伺服器放 Render Free 新加坡（`render.yaml` Blueprint：同樣先裝 pnpm、`ELECTRON_SKIP_BINARY_DOWNLOAD=1` 不下載 Electron、`pnpm build:server`、`pnpm start:server`、健康檢查 `/health`），兩邊都從 `main` 自動部署。伺服器讀環境變數 `ALLOWED_ORIGINS`（逗號分隔、`*` 只比對英數與連字號），三個地方檢查：比對房間的 HTTP 請求用 **static** `onAuth`（實例的 `onAuth` 在 0.18 是 WebSocket 連上時才呼叫，比對階段已經保留了座位）、WebSocket 升級（`beforeUpgrade`，含斷線重連直接開的連線）、CORS（只回允許的來源；Colyseus 會先放預設的 `Access-Control-Allow-Origin: *` 再合併，有清單時從預設標頭拿掉）。沒有 Origin 的請求（健康檢查、Node 客戶端）允許；沒設定清單時全部允許（本機開發）。Electron 正式版的 Origin 是 `null` / `file://`，`multiplayer` e2e 改用正式的來源設定驗證。連線中或重新連線中超過 4 秒，狀態下方提示「伺服器可能正在從休眠中醒來」（Render 免費方案閒置 15 分鐘休眠）。沒有加 `package.json` 的 `packageManager`（平台的安裝指令已指定版本，避免本機 corepack 行為改變）。
- **T-176 攻擊與施法的同步只是表現**（任務 11E，使用者回報「拳、刀砍、魔法對方都看不到」）：協定升到版本 2，新增客戶端訊息 `action`（近戰招式 id；法術 id、`cast` / `release`、朝向、流星雨落點）與 `equip`（武器 id，同步到 `PlayerState.weapon`）。伺服器只檢查格式、id 在資料內、每秒最多 8 則，轉送給其他人（`broadcast` 排除自己），不結算傷害——怪物仍是各客戶端各自一份（T-169），要共享怪物與傷害等 Phase 6 伺服器權威。接收端依動作的 `t`（與位置同一個時間軸）在呈現到那一刻時才播放，動作與插值後的位置對齊；只傳 id，動畫、速度、持續時間、特效依資料。遠端玩家顯示裝備的武器、出招時的招式動畫與揮砍拖尾（`WeaponTrail` 改成可傳入取樣來源）、施法時拿魔杖；法術特效在對方位置重畫（腳下魔法陣、衝擊波、直飛的星光彈、流星），星光彈與流星標記 `visualOnly`，不命中本機的怪物、不震動鏡頭、不播音效。舊版客戶端（協定 1）會被拒絕加入，正式網址更新後要重新整理頁面。
